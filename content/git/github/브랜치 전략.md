최종적으로 안정적인 소프트웨어 배포 보장

Git workflow라고도 불린다.

대표적인 브랜치 전략
1. Git - flow
- 2010년, nvie라는 닉네임을 사용한 빈센트 드리센에 의하여 알려짐
- 브랜치 5단계
	- feature
	- develop
	- release
		- 여러 feature들의 통합테스트를 위함이 목적
	- hotfix
	- main
- 각 기능을 개발이후 develop 브랜치에 merge한 뒤 수동테스트를 거친 이후, 문제 미 발생시 main 브랜치에 merge 한다.
- 앱 애플리케이션에 적합함 


2. Github - flow
-  2011년, GitHub CIO인 Scott Chacon의 제안
- Git - flow가 가진 가장 큰 문제는 개발자가 요구하는 상황보다 훨씬 더 복잡한 프로세스 워크플로우는 단순할수록 오버헤드가 발생하지 않는다.
- 브랜치 전략을 이해하지 못하여 생기는 문제가 사라진다.
- 브랜치 정책
	- main 브랜치는 언제든지 배포 가능
	- 모든 브랜치는 main 브랜치에서 파생
	- local 브랜치에 commit 정기적으로 remote 브랜치로 push
	- 도움이 필요하거나, 코드 병합할 준비가되면 pull request 생성
	- 다른 사람이 변경된 코드를 승인하면 main 브랜치에 merge
	- main 브랜치는 즉시 배포 가능한 상태 유지
