# 1. 분산 환경과 DB 트랜잭션의 원자성
- https://www.geeksforgeeks.org/dbms/acid-properties-in-dbms/
## 1.1. ACID
 - 단일 DB 트랜잭션의 신뢰성 기준으로 여겨지는 ACID
 - 원자성(**Atomicity**), 일관성(**Consistency**), 격리성(**Isolation**), 지속성(**Durability**)
	1. Atomicity
		- all - or - nothing
	2. Consistency
		- 모든 규칙, 제약, 관계가 적절한 상태를 유지하는가
		- 위의 규칙들을 위반할 경우, 잘못된 상태에서 rolled back 되는가
		- 도메인이 가지는 불변식
			- DB의 트랜잭션으로 정의하는 동작
			- Ex) 은행 송금 시, 송금자와 피송금자의 잔액 총합 유지
	3. Isolation
		- 트랜잭션이 서로 영향주는 것 없이 독립적인가
			- 독립성이 깨지는 상황
				- Dirty reads: uncommitted 데이터를 읽는 것
				- Non-repeatable reads: 두 번의 read 사이에 데이터가 변하는 것
				- Phantom read: 트랜잭션 수행 중 새로운 행의 생성
	4. Durability
		 - 커밋된 트랜잭션의 변화는 영구적으로 저장하는가
		 - DB 시스템(범위가 큰 실패)이 실패하더라도 최근 커밋된 상태를 온전히 유지하는가

## 1.2. 분산환경과 트랜잭션

>트랜잭션은 단일 장애 도메인 안에서만 자연스럽게 성립한다.  
분산 환경에서 트랜잭션을 적용하려면 2PC 같은 강한 제약이 필요하며,  
그렇지 않다면 각 트랜잭션이 동일한 제약이나 불변식을 공유하지 않는다는 것이 보장되어야 한다.

# 2. 2PC (Two-Phase Commit)
- 분산환경 트랜잭션을 위한 컴포넌트가 2개의 phase를 나누어 각각의 phase 마다 확인, 커밋을 수행
## 2.1. 특징
- 분산환경 트랜잭션(글로벌 트랜잭션)을 위한 새로운 컴포넌트 존재
	- 새로운 컴포넌트(코디네이터, 트랜잭션 매니저)
- Two - Phase로 동작
	- 1 phase: 각 노드에 prepare 요청을 통해 커밋 가능여부 질의
	- 2 phase: 모든 참여자가 Yes시 commit 요청 및 수행, 어느 하나 no시 모든 노드들에 abort 요청

## 2.2. 동작과정
1. 애플리케이션이 분산 트랜잭션 필요 시, 코디네이터에게 **트랜잭션 ID 요청**
	- 트랜잭션 ID는 글로벌하게 유니크
2. 애플리케이션이 각 참여자와 싱글-노드 트랜잭션을 시작하고 글로벌하게 유니크 ID 전달
	- 싱글-노드 트랜잭션에서 모든 일기와 쓰기 처리
	- 일부 작업 오류시 코디네이터 혹은 모든 참여자 abort 가능
3. 애플리케이션이 커밋 준비 상태 후, 코디네이터가 모든 참여자들에게 prepare 요청
	- 하나의 참여자라도 타임아웃 혹은 실패시 코디네이터가 해당 트랜잭션 ID의 트랜잭션 abort 요청
4. 참여자가 prepare 요청을 받으면, 참여자는 트랜잭션 커밋 준비(트랜잭션 데이터 디스크 작성, 제약위반 검증)
	- 각 노드들은 커밋을 약속
5. 코디네이터가 모든 prepare 요청에 대한 응답을 받은 후, 트랜잭션을 커밋할지 abort할지 결정
	- 코디네이터는 발생가능할 crash에 대비
		- 코디네이터 트랜잭션 로그에 기록
6. 코디네이터의 결정이 디스크에 write 되고 커밋 혹은 abort 요청이 모든 참여자들에게 전송
	- 요청 실패, 타임아웃시 코디네이터는 **성공할 때까지 재시도**
> 2PC의 원자성 보장 
> phase 1의 참가자의 응답이 모두 yes일시 phase 2 진행
> phase 2의 결정이 번복되어지지 않음

## 2.3. 취약점
- 코디네이터가 각 노드의 abort 권한을 소유하므로, 작업 중 코디네이터의 다운시 노드 작업 abort 불가
