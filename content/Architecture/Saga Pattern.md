
# 1. 데이터 일관성
- 기존 모놀리식 환경에서 하나의 DBMS가 트랜잭션의 원자성과 일관성을 보장함
- MSA에서는 하나의 기능이 여러 개의 마이크로서비스에 걸쳐 동작
	- 전체 트랜잭션이 하나의 서비스가 아닌 여러 마이크로서비스에서 로컬 트랜잭션들이 조합된 형태
**MSA 문제점**
- DBMS 범위의 트랜잭션이 아닌, 서비스 로직 수준의 원자성이 보장되어야함

# 2. Saga Pattern
**목적**
- MSA([[MicroService Architecture]]) 환경에서 데이터의 일관성을 보장하기 위함
**특징**
- 각 서비스가 자체적으로 수행하는 로컬 트랜잭션의 흐름을 메시지 또는 이벤트를 통해 이어가는 방식
- 문제 발생시, 롤백이 아닌 **보상조치 트랜잭션** 실행

# 3.사가 vs 2PC
## 3.1. [[2PC (Two-Phase Commit)]] 방식
**특징**
- 하나의 분산 트랜잭션이 여러 데이터베이스에 걸쳐 있을 때 2Phase를 통해 원자성을 보장함
	- prepare
		- 모든 참여자가 커밋이 가능한지 먼저 확인
	- commit
		- 모두 준비시 한꺼번에 커밋
**문제점**
- 트랜잭션 전체를 조율하는 Coordinator의 문제 발생시, 트랜잭션이 끝나지 못하고 모든 참여 서비스가 대기상태에 빠짐
- 여러 시스템이 동시에 처리되는 동안, 각 데이터베이스가 트랜잭션 락을 오랫동안 유지
- 참여 노드 수가 커질 수록, 복잡도 및 실패율 상승

## 3.2. 사가(Saga)
### 3.2.1. 사가 사용 방법
1. Choreography 방식
	- 각 로컬 트랜잭션이 도메인 이벤트를 발행 후 해당 이벤트가 다른 서비스의 로컬 트랜잭션을 트리거함
2. Orchestration 방식
	- 객체가 각 서비스에게 어떤 로컬 트랜잭션을 실행할지 지시하는 방식

### 3.2.3. 문제점
- 보상 트랜잭션 설계 부담
    - 각 로컬 트랜잭션이 실패했을 때 실행할 **보상(Undo) 트랜잭션**을 반드시 직접 정의해야 한다.
    - 모든 작업이 항상 원자적으로 되돌려질 수 있는 게 아니므로(예: 이메일 발송, 외부 결제 승인 등), 완전한 롤백이 불가능한 경우가 발생한다.
        
- 격리성(Isolation) 부족
    - 전통적인 DB 트랜잭션(ACID)과 달리, 사가는 분산 환경에서 **동시 실행 시 일관성 충돌**이 발생할 수 있다.
    - Ex) 재고 감소 Saga가 동시에 여러 번 실행되면 일시적으로 잘못된 재고 수량이 노출될 수 있음.
    - 따라서 **낙관적 잠금(Optimistic Locking)**, **버전 관리(Versioning)**, **Idempotency** 같은 별도 보완 설계가 필요하다.
