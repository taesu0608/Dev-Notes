# 1. Facade Pattern
- **정의**: 복잡한 서브시스템을 단순한 인터페이스로 감싸서 쉽게 사용할 수 있도록 해주는 패턴
- 다른 디자인 패턴(전략 패턴, 팩토리 패턴)과 다르게 **클래스 구조가 비정형화**된 패턴
- Cf) 퍼사드(Facade)는 건물의 정면이 있는 외벽을 의미
	- 같은 어원으로는 얼굴(face)가 있음
## 1.1. 퍼사드 패턴 구조
![[Pasted image 20260323183108.png]]
1. Facade: 서브시스템 기능 편의성을 목적으로 복잡한 로직을 재정리하여 높은 레벨의 인터페이스를 구성
	- 서브시스템과 클라이언트가 서로 긴밀히 연결되지 않도록 구성
2. Additional Facade: 퍼사드들은 사용 사례에 따라 계층적이거나 독립적인 관계로 구성 가능
3. SubSystem: 여러 라이브러리 혹은 클래스
4. Client: 서브 시스템에 직접 접근하는 대신 Facade 사용

### 1.1.1. 재귀적인 Facade 패턴의 적용
- **Additional Facade의 사용**
	- 설계자는 필요에 의해 여러 Facade들이 의존, 독립 관계를 구성하며 시스템 사용의 편리성을 향상시킨다.

# 2. 퍼사드 패턴 특징
## 2.1. 패턴 사용 시기
- 시스템 복잡성이 높을 경우
- 간단한 인터페이스로 복잡한 시스템을 접근하고 싶은 경우
- 사용하는 시스템이 외부와 결합도가 너무 높아 의존성을 낮춰야 할 경우

### 2.1.1. 장점
1. 하위 시스템의 복잡성에서 코드를 분리하여, 외부에서 시스템 사용이 용이해짐
2. 스템 간의 의존 관계가 많을 경우 이를 감소시키고 의존성을 한 곳으로 모음

### 2.1.2. 단점
1. 퍼사드가 앱의 모든 클래스에 결합된 God 객체가 될 수 있다.
2. 퍼사드 클래스 자체가 서브시스템에 대한 의존성을 지님
3. Trade Off
	- 복잡한 시스템의 추상화로의 이점 vs 추가적인 유지보수 비용

# 3. 퍼사드 패턴 적용 예시
## 3.1. JDBC
[[JDBC]]: Java 애플리케이션이 데이터베이스와 통신할 수 있도록 해주는 표준 API 패키지
- JDBC 내 클래스
	1. Cache
	2. DBMS
	3. Row
	4. Message
### 3.1.1. JDBC 조회 규칙
1. DBMS 조회 전 과거 조회된 데이터인지 탐색
2. 캐시에 데이터 존재 시, 캐시 내 데이터 가공 및 출력
3. 캐시에 데이터 부재 시, DBMS를 통해 조회
4. 조회된 데이터 가공 및 출력 + 캐시 저장
- 데이터 가공은 Message 클래스를 사용해야 한다.

### 3.1.2. JDBC와 퍼사드 패턴
- 파사드 패턴을 활용하면 라이브러리 사용 시 사용자가 다뤄야 할 로직이 단순해짐
