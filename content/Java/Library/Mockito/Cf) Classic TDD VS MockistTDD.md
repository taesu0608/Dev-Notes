## 1. 테스트 더블(Double)과 협력 객체

### 1.1. Double Test
- 스턴트 대역(Stunt double)에서 유래
- 테스트에서 실제 객체의 행동을 흉내내는 객체

### 1.2. 유형 및 예시

| 종류        | 목적                      | 특징 및 예시                               |
| --------- | ----------------------- | ------------------------------------- |
| **Dummy** | 전달은 되지만 사용되지 않음         | `null`, 빈 객체, `new Object()` 등 단순 전달용 |
| **Fake**  | 간단한 동작 구현 (진짜는 아님)      | 인메모리 DB, 인메모리 캐시 등                    |
| **Stub**  | 고정된 결과 반환 (상태 확인용)      | 특정 입력 → 특정 출력 반환, 상태 기반 테스트           |
| **Mock**  | 특정 메서드 호출 여부 검증 (행위 확인) | `verify(...)` 등을 통해 검증                |
| **Spy**   | 실제 객체 감시, 호출 여부 + 결과 확인 | Mockito의 `spy(...)` 사용                |

### 1.3. SUT / Collaborators
- **SUT (System Under Test)**: 테스트 대상 클래스
- **협력 객체 (Collaborators)**: SUT가 의존하는 클래스

### 1.4. Sociable vs Solitary
- **Sociable Tests**: 테스트 대상이 다른 유닛과 함께 동작
- **Solitary Tests**: 테스트 유닛을 격리하여 동작

## 2. 테스트 준비 방식

### 2.1. Fixture (고정된 협력 객체)

- **정의**: 테스트 실행 전에 미리 준비해두는, 일정한 상태를 가진 객체나 환경
- 주 용도: 여러 테스트에서 반복적으로 사용하는 **공통 설정값**을 제공
- 특징:
  - 클래스 기반 구성 → **재사용성**, **유지보수성**이 높음
  - 주로 **상태 기반 테스트**와 함께 사용

```java
@BeforeEach
void setUp() {
    user = new User("Alice");
    userRepository = new InMemoryUserRepository();
    userService = new UserService(userRepository);
}
```

### 2.2. Mock (목 객체)

- **정의**: 테스트 대상의 협력 객체를 흉내 내는 가짜 객체로, **행위 검증**을 목적으로 사용
- 주 용도: 테스트 대상이 **어떤 행위를 수행했는지** 확인하거나, 외부 의존성을 격리할 때 사용
- 특징:
  - 프레임워크(Mockito 등)를 통해 동적으로 생성
  - 테스트마다 유연하게 구성 가능 → **독립성**, **유연성** 높음
  - 주로 **행위 기반 테스트**와 함께 사용
  
```java
class UserServiceTest {

    @Test
    void testSaveUser_callsRepositorySave() {
        UserRepository mockRepo = mock(UserRepository.class);
        UserService userService = new UserService(mockRepo);

        userService.saveUser(new User("Alice"));

        verify(mockRepo).save(any(User.class)); // 행위 기반 검증
    }
}
```

| 구분     | 장점                                                                 | 단점                                                                 |
|----------|----------------------------------------------------------------------|----------------------------------------------------------------------|
| Fixture  | - 같은 설정 반복 방지<br>- 유지보수 용이<br>- 테스트 의도 명확       | - 의존성 변경 시 전체 수정 필요<br>- 설정이 커지면 테스트 속도 저하 가능 |
| Mock     | - 테스트마다 유연하게 설정 가능<br>- 단위 테스트에 적합<br>- 독립성 보장 | - 상태 검증 어려움<br>- 구현 세부에 종속된 테스트가 될 위험 있음       |

## 3. 검증 방식

### 3.1. 상태 검증 (State Verification)

- 테스트 실행 후 시스템 또는 객체의 상태 변화가 기대한 결과와 일치하는지를 확인하여, 기능이 정확하게 수행되었는지를 판단하는 방식
- 주 용도: 실제 객체의 내부 상태나 반환 값을 확인하여 검증할 때 사용
- 특징
	- 테스트의 안정성이 높음
	- **구현 세부 사항**에 대한 의존도 낮음
- Ex) 메서드 호출 이후 데이터베이스나 메모리 상의 값이 예상대로 변경되었는지 확인


### 3.2. 행위 검증 (Behavior Verification)

- 테스트 대상이 특정 메서드나 동작을 수행했는지를 확인하여, 예상한 행위가 실제로 발생했는지를 검증하는 방식
- 주 용도: 외부 시스템이나 협력 객체와의 상호작용이 중요한 경우, 해당 상호작용이 정확히 수행되었는지를 검증할 때 사용
- 특징
	- 주로 Mock 객체와 함께 사용
	- 테스트가 구현 방식에 민감
	- 유지보수가 어려움
- Ex) 서비스 호출 후 협력 객체의 save(), notify() 등이 호출되었는지 검증
### Cf) 상태 기반 검증과 행위 기반 검증의 차이
- **상태 기반 검증**:  
  실제 객체를 사용하여 테스트를 수행하며, 특정 작업 이후 객체의 **상태 변화**를 확인함으로써 테스트의 성공 여부를 판단한다.  
  → Ex) 저장 후 데이터가 DB나 컬렉션에 존재하는지 확인
- **행위 기반 검증**:  
  가짜(Mock) 객체를 사용하여 테스트를 수행하며, 특정 작업 이후 **어떤 메서드가 호출되었는지**를 확인함으로써 테스트의 성공 여부를 판단한다.  
  → Ex) `save()` 메서드가 호출되었는지 `verify()`로 확인

## 4. 테스트 철학 비교

테스트 주도 개발(TDD) 방식에서 개발자는 테스트 대상과 협력 객체를 어떻게 다룰 것인지에 따라 두 가지 관점으로 나뉜다.  
바로 **Classicist(상태 기반 접근)** 와 **Mockist(행위 기반 접근)** 이다.

### 4.1. Classicist

- 실제 구현 객체를 그대로 사용하여 테스트를 수행하는 접근 방식
- 협력 객체와의 관계를 유지한 채, 전체 시스템의 흐름을 검증하려는 성향이 강함
- 외부 의존성이 있더라도 최대한 **Stub** 수준에서 처리하며, 대부분 **상태 기반 테스트**를 선호
- 테스트는 실제 시나리오에 가깝고, 시스템의 통합적 관점을 중시함

→ 장점: 테스트가 실제 사용 흐름에 가까워 안정적이고 현실적인 검증 가능  
→ 단점: 외부 시스템 변화나 상태 이상이 전체 테스트 실패로 이어질 수 있음

### 4.2. Mockist

- 테스트 대상 객체 외의 모든 협력 객체를 **Mock**으로 대체하여 테스트를 수행
- 각 객체의 행위와 책임을 명확히 분리하여 검증하며, 객체 간 상호작용에 집중
- 모든 협력 객체를 가짜로 대체하기 때문에, 테스트는 철저히 **행위 기반 검증**으로 이루어짐
- 객체지향적 설계를 촉진하며, 작은 단위의 기능을 세밀하게 테스트하기 적합

→ 장점: 각 객체를 독립적으로 테스트할 수 있어 빠른 피드백과 설계 유도에 유리  
→ 단점: 내부 구현 변경에 민감하며, Mock 설정이 과해지면 테스트 신뢰도 저하

## 5. 비결정적 테스트와 Mock의 활용

### 5.1. 비결정적 테스트란?

- 테스트를 여러 번 실행할 때 **결과가 일관되지 않게 달라지는 테스트**를 의미함
- 주로 다음과 같은 외부 요인에 의해 발생함:
  - 외부 API 호출
  - 네트워크 지연 또는 오류
  - 멀티스레드 환경의 동시성 문제
  - Ex) 실제 결제 시스템 등 외부 상태에 따라 달라지는 환경

→ 이러한 테스트는 **테스트 신뢰도를 떨어뜨리고**, **디버깅을 어렵게 만들며**, **CI 환경에서 테스트 실패를 유발**함
### 5.2. 해결책: Mock을 이용한 외부 환경 격리

- 외부 시스템이나 의존성을 **Mock 객체로 대체**하여 테스트의 제어권을 확보
- 테스트 환경을 **결정론적(Deterministic)** 으로 만들 수 있음
- 예: 실제 결제 API 대신 응답을 시뮬레이션하는 Mock 객체 사용

→ 이렇게 하면 테스트는 **항상 같은 조건과 결과**로 실행되며, **신뢰성과 안정성**을 확보할 수 있음

### 5.3. 결론
- **Mockist** 접근은 본질적으로 **비결정적 요소를 테스트에서 제거**하려는 목적과 일치함
- 하지만 모든 테스트에 Mock을 사용하는 것은 오히려 테스트 유지보수를 어렵게 만들 수 있으므로, **상황에 따라 Classicist와 Mockist의 균형 잡힌 활용**이 중요함

## 6. 테스트 변경 가능성 비교

### 6.1. Mockist
- 테스트 목적 변경 시 테스트 코드도 함께 변경 필요

### 6.2. Classicist
- 테스트 목적 변경되어도 기존 테스트 유지 가능

***
## 7. Test Isolation (테스트 격리)

- Classicist는 협력 객체의 문제로 전체 테스트 실패 가능성 있음
- Mockist는 각 클래스가 명확히 분리되어 세분화된 테스트 용이
- 클래식 스타일은 테스트 세분화를 놓치기 쉬움

***
## 8. TDD 디자인 스타일

### 8.1. Inside-Out

- 리팩토링 단계에서 디자인 도출
- 빠른 피드백 가능
- 오버 엔지니어링 방지
- 시스템 전체 이해 없이 시작 가능
- 초보자에게 적합
- 협력 객체 설계가 어색하거나 Public API가 잘못 설계될 수 있음

### 8.2. Outside-In

- 외부부터 내부로 설계 (Controller → 기능)
- 테스트 red 단계에서 설계 도출
- 협력 객체의 API가 자연스레 도출
- 객체지향적인 코드 작성에 유리
- 설계 지식이 필요하며, 숙련자에게 적합
- 오버 엔지니어링 가능성 있음
