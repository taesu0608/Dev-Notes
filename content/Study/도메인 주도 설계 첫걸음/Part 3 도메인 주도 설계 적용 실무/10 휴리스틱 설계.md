# 1. 휴리스틱
- 불확실하거나 정보가 부족한 상황에서 빠르고 효율적으로 판단을 내리기 위한 경험에 기반한 어림짐작이나 간편한 규칙

# 2. 바운디드 컨텍스트
## 2.1.  최적의 바운디드 컨텍스트
> 한 서비스의 경계를 정의하는 데 있어 식별을 용이하게 해주는 유용한 휴리스틱은 매우 많다. 그러나 그중 크기(size)로 경계를 구분하는 것은 가장 도움이 되지 않는다.

**바운디드 컨텍스트 경계 범위 설정에 효과적인 휴리스틱**
- 넓은 바운디드 컨텍스트의 경계를 설정하여 필요에 따라 경계를 쪼개는 것이 효율적임

# 3. 비즈니스 로직 구현 패턴
**비즈니스 로직 모델링 방법**
1. 트랜잭션 스크립트
	- 지원 하위 도메인, 일반 하위 도메인을 위한 솔루션에 적합
	- 단순한 자료구조
2. 액티브 레코드
	- 캡슐화: 복잡한 자료구조를 하부 데이터베이스에 매핑
3. 도메인 모델
4. 이벤트 소싱
	-  심층적 분석 필요가 있는 핵심 하위 도메인에 적합

**비즈니스 로직 선정에 효과적인 휴리스틱**
1. 하위 도메인이 심층적 분석(감사 로그, 통화 트랜잭션 추적)을 요청하면 이벤트 소싱 도메인 모델
2. 하위 도메인의 비즈니스 로직이 복잡하다면 도메인 모델
3. 복잡한 자료구조를 포함하면 액티브 레코드 패턴
4. 나머지 트랜잭션 스크립트

핵심 하위 도메인이 트랜잭션 스크립트가, 지원 하위 도메인이 이벤트 소싱 도메인 모델이 적합할 수도 있다. 이때는 내가 적용한 휴리스틱을 다시 살펴봐야한다.

# 4. 아키택처 패턴
## 4.1. 아키택처 패턴
- 계층형 아키텍처
- 포트와 어댑터
- CQRS(command-query responsibility segregation

**아키텍처 패턴 휴리스틱**
- 이벤트 소싱 도메인 모델은 CQRS가 필요하다.
	- 그렇지 않다면 시스템은 데이터 질의 옵션이 극심하게 제한되어 자신의 ID만으로 단일 인스턴스를 가져와야 한다.
- 도메인 모델은 포트와 어댑터 아키텍처가 필요하다.
	- 계층형 아키텍처에서는 영속성에 대한 고려 없이 에그리게이트와 밸류 오브젝트를 만들기 어렵다.
>도메인 모델이 포트와 어댑터 아키텍처를 필요로 하는 이유는, **도메인 로직을 인프라스트럭처로부터 독립적으로 유지하기 위해서**다.  
사용자의 요청이나 외부 시스템과 교환하는 데이터 형식은 도메인이 다루는 정보와 다르기 때문에, 이 둘을 분리하는 **포트(인터페이스)**와 **어댑터(구현체)** 구조가 필요하다.
반면 계층형 아키텍처에서는 비즈니스 로직과 영속화가 흐름상 강하게 결합되기 쉽다. 그러다 보니 **도메인 모델이 DB 설계에 종속**되고, 순수하게 비즈니스를 표현하는 **Entity, Value Object, Aggregate**를 설계하기가 어렵다. 즉, 영속성에 대한 고려 없이 도메인을 설계하는 것이 힘들어지는 것이다.****
- 액티브 레코드 패턴은 애플리케이션(서비스) 계층을 추가한 계층형 아키텍처와 잘 어울린다.
	- 액티브 레코드를 제어하는 로직을 위한 것
- 트랜잭션 스크립트 패턴은 세 개의 계층만으로 이어진 최소한의 계층형 아키텍처를 적용가능하다.

## 4.2. 테스트 전략
![[Pasted image 20250911194055.png]]
**피라미드형 테스트**
- 단위테스트에 집중
- 애그리게이트와 밸류 오브젝트 도메인 모델 패턴 잘 지원함

**다이아몬드형 테스트**
- 통합테스트에 집중중
- 액티브 레코드 패턴 사용시 효과적
	- 시스템의 비즈니스 로직이 서비스 계층과 비즈니스 로직 계층으로 흩어지므로 두 계층간의 연동을 잘 확인할 수 있음

**역전된 피라미드형 테스트**
- 엔드 - 투 - 엔드 테스트에 집중
- 트랜잭션 스크립트 패턴을 구현한 코드베이스에 어울림.
