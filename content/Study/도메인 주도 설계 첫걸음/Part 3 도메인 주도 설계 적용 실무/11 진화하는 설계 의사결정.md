- 소프트웨어 프로젝트 환경의 변화가 소프트웨어 설계 의사결정에 끼치는 영향
---
# 1. 도메인 변경
## 1.1. 핵심에서 일반으로
핵심 도메인이 제공하던 솔루션을 더 나은 성능으로 상용 제품이 등장하면 핵심 도메인은 경쟁력을 잃으며 일반도메인으로 간주된다.
## 1.2. 일반에서 핵심으로
일반 도메인의 솔루션을 더 나은 성능으로 개선시키거나 상용화 솔루션이 아닌 독자적 솔루션으로 바꾸면서 경쟁력이 생기며 핵심 도메인으로 활용 가능해진다.

## 1.3. 지원에서 일반으로
- 기존 사내 솔루션을 상용 솔루션으로 변경하며 지원 도메인이 일반 도메인이로 변한다.

## 1.4. 지원에서 핵심으로
- 지원 솔루션이 CRUD 인터페이스 혹은 ETL 프로세스에 따르지 않고 과도한 비즈니스 로직으로 구성되어진다면 이에 따른 이유가 분명 존재한다. 이는 해당 프로세스가 회사의 프로세스에 이익이 될 가능성이 있음을 의미한다.

## 1.5. 핵심에서 지원으로
- 핵심 도메인이 복잡성에 비해 수익성이 없는 경우 발생한다. 이는 핵심 도메인을 지원도메인으로 바꾸며 불필요한 복잡성을 줄일 수도 있다.

## 1.6. 일반에서 지원으로
- 상용 솔루션 혹은 오픈소스 솔루션의 통합 과정에서의 복잡성 대비 이점이 낮을 경우 다시 사내 솔루션에 의존을 택할 수 있다.
---
# 2. 전략적 설계 문제
- 하위 도메인의 유형의 변경은 바운디드 컨텍스트에 직접적인 영향을 끼침
	- Ex) 핵심 하위 도메인은 충돌 방지 계층을 통해 오픈 서비스와의 빈번한 변경으로부터 서비스를 보호해야함
	- Ex) 분리형 노선(각 바운디드 컨텍스트에서 동일한 도메인을 각기 구현하여 사용하는 경우)인 지원 하위 도메인이나 일반 하위 도메인이 핵심 하위 도메인으로 변경되어지면 대부분 한 팀에서 핵심 하위 도메인이 설계가 되어진다. 이때 기존의 지원,일반 하위 도메인을 사용하던 바운디드 컨텍스트와 핵심 하위 도메인이 속한 바운디드 컨텍스트는 사용자-제공자 관계가 적합하다.
---
# 3. 전술적 설계 문제
## 3.1. 트랜잭션 스크립트에서 액티브 레코드로
- 트랜잭션 스크립트와 액티브 레코드 패턴은 절차지향 스크립트란 점은 같지만 자료구조를 모델링하는 방식에 차이가 있음
- 데이터 베이스에 직접 접근하는 대신 엑티브 레코드를 사용하여 모델과 구조를 추상화
## 3.2. 액티브 레코드에서 도메인 모델로
- 엑티브 레코드의 불일치 및 중복이 많아질 경우 도메인 모델 패턴으로 리펙토링의 필요성 증가
- 도메일 모델로의 전환 휴리스틱
	- Value Object를 식별
		- 객체의 불일치 및 코드 복잡성 완화
	- private setter
		- 비즈니스 로직의 객체 수정부분을 컴파일 시점에서 발견하고, 캡슐화를 통한 관리 유도
	- private 메서드
		- 클래스마다의 메서드가 아닌 인터페이스의 메서드 사용 유도

## 3.3. 도메인 모델에서 이벤트 소싱 도메인 모델로
- 직접적인 데이터 조작을 하는 도메인 모델에서 수명주기를 기반으로 하는 이벤트 소싱 도메인 모델로의 전환
### 3.3.1. `이력이 없는 상태`를 이벤트 기반 모델로 마이그레이션 시 주의사항
#### 1. 전환이 필요한 과거 이력 생성
- 변환전 데이터를 기반으로 특정 상태의 이벤트 소싱 히스토리는 생성 가능하다.
- 하지만 몇몇 상태의 이벤트는 확인조차 불가하다

#### 2. 마이그레이션 이벤트 모델링
- 명시적으로 마이그레이션 이벤트를 정의하여 이벤트 스트림 초기화

# 4. 조직 변화
## 4.1. 파트너십에서 사용자-제공자로
- 강력한 의사소통을 전제로하는 파트너십 패턴은 회사의 규모가 커짐에 따라, 협력 패턴이 변함
## 4.2. 사용자-제공자에서 분리형 노선으로
- 팀간의 의사소통 문제 혹은 조직 내부 정치, 지리적 거리등을 이유로 통합의 문제를 겪게 된다.
- 어떤 시점에서는 서로의 꼬리를 쫓는 대신 기능을 복제하는 분리형 노선이 효과적일 수 있다.
---
# 5. 도메인 지식
- 도메인 지식 수준에 따라 바운디드 컨텍스트의 경계를 설계하는 휴리스틱
	- 도메인 지식 수준이 낮을 수록 바운디드 컨텍스트의 경계를 크게 구성해라
- 도메인의 이해가 깊어지고 비즈니스 로직이 안정화됨에 따라 컨텍스트는 분해 가능해진다.
	- 더 작은 바운디드 컨텍스트
	- 마이크로서비스
## 5.1. 도메인 변화의 문제점
- 새로운 도메인 지식을 통해 설계를 발전시키고 회복성(resilience)을 높여야 한다.
- 도메인 변화는 기존의 도메인 지식의 손실을 발생시킨다.
	- 이후 임시변통 코드들이 더해지며 코드베이스는  복잡성 및 불확실성이 커진다.
- **회복성**: 오류가 있어도 프로그램 수행을 계속할 수 있는 시스템의 능력

## 5.2. 이벤트스토밍(EventStorming)
- 도메인 지식의 퇴보를 사전에 방지하는 효과적인 도구
---
# 6. 성장
## 6.1. 시스템의 성장
- 시스템이 건강하다는 신호

## 6.2. 하위 도메인
- 완벽한 경계가 아닌 유용한 경계를 목적으로 해야함

## 6.3. 바운디드 컨텍스트
- 성장은 기존의 암시적 문제를 부각시킨다.
- 복잡해진 바운디드 컨텍스트는 다른 바운디드 컨텍스트를 호출하지 않고는 작업을 완료할 수 없데 되었음을 확인할 수 있다.

## 6.4. 애그리게이트
- 경험상 애그리게이트는 가능한 한 작게 유지하고, 비즈니스 도메인에서 강력하게 일관적인 상태를 유지해야 한다.
