# 1. 실무
**목적**
- 브라운필드 프로젝트의 DDD 패턴을 적용하기 위한 전략을 학습

- DDD의 도메인 분석, 전략적 의사결정, 전술적 의사결정, 도메인 주도 설계 도구들을 배웠지만 현실은 이모든 것이 적용되는 그린필드 프로젝트가 아니다.
- 그러나 DDD는 브라운필드의 상황에서 효과적이다.
- **Greenfiled**
	- 소프트웨어 개발 에서 그린필드 프로젝트는 다른 시스템, 특히 레거시 시스템과의 통합을 고려하지 않고 완전히 새로운 환경을 위한 시스템을 개발하는 프로젝트
- **Brownfiled**
	- 브라운필드(Brownfiled) 개발은 정보 기술 산업에서 기존(레거시) 소프트웨어 애플리케이션/시스템이 바로 존재하는 환경에서 새로운 소프트웨어 시스템을 개발하고 배포해야 하는 문제 공간을 설명하는 데 일반적으로 사용되는 용어

# 2. 전략적 분석
- 실무에서 DDD 도입의 좋은 출발점은 조직의 비즈니스 전략과 시스템 아키텍처의 현 상황을 이해하는 것

## 2.1. 비즈니스 도메인 이해하기
- 조직의 비즈니스 도메인은 무엇인가?
- 고객은 누구인가?
- 조직이 고객에게 제공하는 서비스 또는 가치는 무엇인가?
- 경쟁 회사 또는 그들의 제품은 무엇인가?


## 2.2. 도메인 구별하기
**핵심 하위 도메인**
- a. 경쟁업체와 차별화 되는 점 찾기
- b. 최악으로 설계된 소프트웨어 컴포넌트 찾기
	- 모든 엔지니어가 싫어하지만 수정 시 비즈니스 위험이 수반되기에 처음부터 소스코드를 재구성 하는 것을 꺼림
	- 레거시 시스템을 상용 시스템으로 대체할 수 없음
		- 수정 시 비즈니스 위험이 수반됨
			- 경쟁력 약화, 대체가능성 증가


**일반 하위 도메인**
- 상용 솔루션, 구독 서비스, 연동가능한 오픈소스 소프트웨어 찾기

**지원 하위 도메인**
- 상용 솔루션으로 대체 불가하지만 직접 경쟁우위를 제공하지 않는 소프트웨어 찾기

# 3. 현재 설계 탐색
- 다른 컴포넌트와 독립적으로 개선되고 테스트되고 배포될 수 있는지 확인
## 3.1. 전술적 설계 평가
- 각 상위 수준 컴포넌트에 대해 평가
	- 어떤 비즈니스 하위 도메인을 포함하는가
	- 어떤 기술적 설계 의사결정을 내렸는가
	- 비즈니스 로직 구현 및 컴포넌트 아키텍처에 어떤 패턴을 사용했는가
- 해결 가능 범주를 확인
	- 해당 솔루션의 복잡성이 해결가능한가
	- 더 정교한 설계패턴이 필요한 영역이 있는가
	- 비용을 절약할 수 있는 상용 솔루션을 적용할 수 있는가

## 3.2. 전략적 평가
- 상위 수준 컴포넌트의 지식을 사용하여 해당 컴포넌트를 바운디드 컨텍스트로 취급하여 현 상태를 차트로 표시
- 결과 컨택스트 맵을 분석하고 DDD 관점에서 아키텍처 평가
	- Ex) 평가 휴리스틱 예시
		- 동일한 상위 수준의 컴포넌트에 대해 작업하는 여러팀
		- 핵심 하위 도메인의 중복 구현
		- 하청 회사가 핵심 하위 도메인을 구현
		- 자주 실패하는 연동으로 인한 마찰
		- 외부 서비스와 레거시 시스템에서 확산되는 어색한 모델

## 3.3. 현대화 전략
- 엔지니어가 처음부터 다시 작성하려고 하는 '대대적인 재작성(big rewrite)' 노력은 거의 성공하지 못함
- 따라서 노력을 어디에 투자할지 전략적으로 결정해야함
### 3.3.1. 전략적 결정을 위한 전제 조건
	- 시스템의 하위 도메인 경계를 식별
	- Ex) 논리적 하위 도메인 경계를 재구성
		- As is) 마케팅 바운디드 컨텍스트
			- 마케팅.애플리케이션
			- 마케팅.인프라스트럭처
			- 마케팅.모델
			- 마케팅.모바일
			- 마케팅.서비스
			- 마케팅.UI
		- To be) 마케팅 바운디드 컨텍스트
			- 마케팅.광고소재
			- 마케팅.캠페인
			- 마케팅.최적화
			- 마케팅.퍼블리싱
- 동적 로딩, 리플렉션 등 참조가 끊기지 않도록 주의
- 코드베이스 뿐만 아니라 데이터베이스의 프로시저 명 혹은 스키마에도 적용

### 3.3.2. 전략적 현대화
- 초기부터 가능한 한 작은 바운디드 컨텍스트로 분해하는 것은 위험함
- 논리적 경계를 물리적 경계로 전환하여 가장 많은 가치를 얻을 수 있는 곳을 찾아야함
- **바운디드 컨텍스트 추출하는 과정의 휴리스틱**
	- 여러 팀이 동일한 코드베이스에서 작업하고 있는가? 그렇다면 각 팀에 대한 바운디드 컨텍스트를 정희하여 개발 수명주기를 분리하라
	- 서로 다른 컴포넌트에서 충돌하는 모델을 사용하고 있는가? 그렇다면 충돌하는 모델를 별도의 바운디드 컨텍스트로 재배치하라
- 필요한 최소 바운디드 컨텍스트 발견 시 이들 간의 관계와 연동 패턴을 조사할 것
- 이후 컨텍스트 통합 패턴이 해결할 수 있는 문제에 주목
- **컨텍스트 통합 패턴**
	- 조직의 성장으로 더이상 협업 패턴이 무효화 되었을때 사용자-제공자 관계(순응주의자, 충돌 방지 계층, 오픈 호스트 서비스)로 리펙터링 할것
	- **충돌 방지 계층**
		- 다운스트림 유스케이스: 일반적으로 레거시 시스템에게서 다운스트림으로 구성되어 컴포넌트 확산이 이뤄지는 경우 비효율적인 레거시 모델으로부터 바운디드 컨텍스트를 보호하기 위해 사용
		- 업스트림 유스케이스: 사용하는 업스트림 서비스의 퍼블릭 인터페이스에 대한 잦은 변경으로 바운디드 컨텍스트를 보호하기 윟 ㅐ사용
	- **오픈 호스트 서비스**
		- 한 컴포넌트의 구현 상세에 대한 변경사항이 잦아 사용자에게 악영향을 끼치는 경우 오픈 호스트 서비스 활용
	- **분리형 노선**

## 3.4. 현대화 전술
### 3.4.1. 전술적 현대화
- 비즈니스 가치와 구현 전략의 부조화를 찾는 관점이 유리
	- Ex) 복잡할 가능성이 높은 핵심 하위 도메인에 트랜잭션 스크립트 혹은 액티브 레코드와 같은 부합하지 않는 패턴이 구현된 경우

### 3.4.2. 유비쿼터스 언어 육성
- 도메인 주도 설계의 지름길인 이벤트 스토밍을 활용

### 3.4.3. 스트랭글러 패턴
- 하나의 나무가지에서 싹을 틔워 성장하여 줄기가 해당 나무를 덮게되어 숙주나무가 죽게되는 방식의 스트랭글러 무화과(Strangler fig)의 성장 패턴에서 따옴
- **스트랭글러 마이그레이션 패턴**
	- 새로운 바운디드 컨텍스트
		- 새로운 요구사항 구현
		- 레거시 컨텍스트의 기능 마이그레이션
		- Cf) 핫픽스와 긴급상황을 제외하고 레거시 바운디드 컨텍스트 개발 중지
		- 마이그레이션 하는 과정에서 레거시, 현대 바운디드 컨텍스트 모두 하나의 DB를 사용하며 진행할 수 있음

### 3.4.4. 전술적 설계 의사결정 리팩터링
- 레거시 코드베이스 현대화시 주의점
	- **1. 점진적인 조치가 대규모 재작성보다 안전하다.**
		- 대규모 재작성: 트랜잭션 스크립트, 액티브 레코드 > 이벤트 소싱 도메인 모델
		- 점진적인 조치: 트랜잭션 스크립트, 액티브 레코드 > 상태 기반 애그리게이트 > 이벤트 소싱 애그리게이트
	-  **2. 도메인 모델로의 리펙터링이 한번에 이뤄질 필요는 없다.**
		- 벨류 오브젝트 탐색 등과 같은 작은 절차부터 수행
