
## 1. 단일 애그리게이트 컨텍스트

- 규칙: 한 트랜잭션 = **오직 하나의 애그리게이트 인스턴스만 수정**.
- 결과: 이벤트 스토어 입장에서는
    `aggregate_id = X version = N events = [N+1 ... M]`
    이런 스트림만 관리하면 됨.
    
- 즉, **이 ID의 버전이 몇 번째였는지**만 보면 충돌 감지 가능.
- 그래서 “애그리게이트 ID로 분할 가능하다”는 말이 나옴 → **각 애그리게이트별로 독립적인 이벤트 스트림**을 둘 수 있기 때문.
    

---

## 2. 다중 애그리게이트 컨텍스트

- 규칙 없음: 한 트랜잭션이 **여러 애그리게이트**를 동시에 수정.
    - 예: `주문(Order)`과 `재고(Inventory)`를 한 번에 같이 변경.
- 문제:
    
    1. 이벤트 스토어가 ID로만 나뉘어 있으면,  
        트랜잭션이 **여러 ID 스트림에 동시에 쓰기**해야 함 → 원자성 보장 어려움.
    2. 충돌 감지도 힘듦.
        - A와 B 애그리게이트를 동시에 수정했는데, 중간에 B만 다른 트랜잭션이 바꿔버리면?
        - 단순히 `aggregate_id + version` 체크만으로는 검증 불가.
    3. 결과물이 동시에 두 개일 수 있음 → “동일 트랜잭션인데 A는 성공, B는 실패” 같은 불일치 발생.
        

---

## 3. 정리

- **단일 애그리게이트 컨텍스트**
    - 트랜잭션 단위가 명확히 `aggregate_id` 하나라서,
    - 이벤트 스토어를 **ID별 파티션(샤드)**으로 안전하게 나눌 수 있음.
        
- **다중 애그리게이트 컨텍스트**:
    - 여러 ID가 섞여버리기 때문에,
    - 이벤트 스토어는 단순히 ID별로 나누는 걸로는 **원자성·일관성 보장 불가**.
    - **동시성 충돌과 불일치 문제** 때문.
