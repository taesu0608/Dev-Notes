# 1. 바운디드 컨텍스트 특징
1. 유비쿼터스 언어의 일관성 유지
> 컨텍스트를 나눔으로써 한 단어가 중의적인 의미를 지녀 유비쿼터스 언어의 역할을 저해하는 경우를 제한한다.
2. 모델링 가능
> 추상화는 명확한 경계가 필수적임
> 경계는 "언어의 책임"을 만듬
> 이는 책임 불명확과 해석 차이를 방지하기 위함

3. 바운디드 컨텍스트의 상호작용 
	바운디드 컨텍스트의 모델
	- 독립적으로 발전 및 구현 가능
##### 바운디드 컨텍스트 구현체끼리는 상호작용한다.

**Contract**: 바운디드 컨텍스트 사이의 점접

# 2. 컨트렉트(contract)
## 2.1. 컨트렉트의 필요성
다른 컨텍스트 모델은 서로 영향을 끼치므로 조율하여 컨트랙트를 정의해야함

## 2.2. 컨텍스트 간의 연동
서로 다른 컨텍스트끼리의 연동(like 협업)이 필요할 때의 패턴
1. 협력형(cooperation) 패턴 그룹
	- 파트너십 패턴
	- 공유 커널 패턴
2. 사용자 - 제공자
3. 분리형 노선

## 2.3. 협력형 패턴 그룹
### 2.3.1. 파트너십(partnership) 패턴
- **애드혹(ad-hoc)방식**으로 바운디드 컨텍스트 간의 연동조정
- API 변경을 알려 충돌없이 연동이 양방향으로 됨
	- 구축된 협업 실무
	- 높은 수준의 헌신
	- 잦은 팀간 동기화
	- 변경사항의 지속적인 통합
> 애드훅(ad-hoc): "특별한 목적을 위해서"라는 의미의 라틴어
### 2.3.2. 공유 커널(shared kernel) 패턴
- 필요에 의해 모델의 경계임에도 같은 모델이 서로 다른 바운디드 컨텍스트에서 구현되는 경우
![[Pasted image 20250817200212.png]]

- **공유 범위**
	- 공유 커널은 해당되는 바운디드 컨텍스트의 수명주기도 엮이게 함
	- 필요에 의해 최소한의 컨트렉트와 자료구조만으로 구성 요망
- **구현**
	- 단일 저장소 사용
	- 연결 라이브러리
	- 전파
- **공유 커널 사용 경우**
	- 중복 비용(통합 비용)> 조율 비율 경우 공유 커널 사용
	- 레거시 시스템의 현대화
>Cf) Defference between 중복비용 and 통합비용
	- **모델의 변동성**
	모델의 변동성이 커서 통합이 빈번히 요구될때

### 공유커널을 대하는 자세
- 바운디드 컨텍스트의 원칙과 공유커널은 상충됨
	- 바운드디 컨텍스트 원칙 중 단일 팀 원칙
- 통합의 문제(모델 동기화, 설계 의사결정)등을 예방하기 위한 조치
	- 공유 커널 범위를 최소화해 연쇄적 변경의 범위 축소
	- 매 변경시 통합 테스트 시행

## 2.4. 사용자 - 제공자 패턴 그룹
![[Pasted image 20250817205519.png]]
- **업스트림(upstream)**: 서비스 제공자
- **다운스트림(downstream)**: 사용자
- 연동 컨트랜트를 주도하는 권력의 불균형에 따라 패턴이 갈림

### 2.4.1. 순응주의자(conformist) 패턴
- 서비스 제공자(업스트림 바운디드 컨텍스트)에게 힘의 균형이 쏠린 경우
	- 사용자 머무르거나 떠나거나
- Ex) 산업 표준

### 2.4.2. 충돌 방지 계층(ACL: anticorruption layer)패턴
![[Pasted image 20250817205631.png]]
- 순응주의자 패턴에서 다운스트림 바운디드 컨텍스트가 순응하지 않을 경우
	- 충돌 방지 계층을 통해 업스트림 바운디드 컨텍스트의 모델을 필요에 맞게 가공
	1. 다운스트림 바운디드 컨텍스트가 핵심 하위 도메인을 포함할 경우
		- 순응의 가치가 없음
	2. 업스트림 모델이 사용자의 요건에 비효율적이거나 불편한 경우
		- 레거시 시스템 연동시 종종 발생함
	3. 제공자가 컨트랙트를 자주 변경하는 경우
		- 모델을 보호하기 위해 영향 받는 영역을 **ACL**로 제한함

### 2.4.3. 오픈 호스트 서비스 패턴
- 사용자(다운스트림 바운디드 컨텍스트)에게 힘의 균형이 쏠린 경우
![[Pasted image 20250817210441.png]]
- 제공자는 두가지의 언어를 운용함
	- 제공자의 퍼블릭 인터페이스 위한 유비쿼터스 언어
	- **연동 지향 언어(integration-oriented language)** = **공표된 언어(publised language)**
		- 사용자에게 더 편리한 프로토콜

**오픈 호스트 서비스(OHS: open-host service)**
- 제공자가 사용자를 위한 연동 모델을 개발
- 여러 버전의 연동 모델을 동시에 노출 가능

## 2.5. 분리형 노선 패턴
- **분리형 노선(seperated ways) 패턴**
	- 협업이 불가능할때

### 2.5.1. 커뮤니케이션 이슈
- 여러 바운디드 컨텍스트에서 기능을 중복하는 것이 더 효과적

### 2.5.2. 일반 하위 도메인
- 일반 하위 도메인이 일반 솔루션(기존 비즈니스 문제를 해결하는 해결책)과 연동하는 것이 쉽다면 각자 연동하는 것이 효과적일 수 있음
- Ex) 로깅 프레임워크

### 2.5.3. 모델의 차이
- 바운디드 컨텍스트의 모델 간의 차이가 심할 경우

# 3. 컨텍스트 맵
- 시스템의 바운디드 컨텍스트 간의 연동 패턴을 맵으로 표현

### 3.1. 컨텍스트 맵의 장점
- 거시적 설계 관점
- 커뮤니케이션 패턴
	- 팀간의 협력, 충돌 방지 계층, 분리형 노성 패턴간으로 커뮤니케이션 패턴 묘사
- 조직적 문제
	- 팀간의 패턴을 통해 조직적 문제에 대한 통찰력 제공
