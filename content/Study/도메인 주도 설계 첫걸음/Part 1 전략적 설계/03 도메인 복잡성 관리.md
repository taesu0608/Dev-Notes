#### 유비쿼터스 언어가 충돌하는 경우
배경
- 용어 리드(lead)의 충돌
- 리드: 광고를 보고 상품 구매를 위한 홈페이지 접속이 발생한 경우
부서
- 마케팅 부서
	- 누군가가 제품 중 하나에 관심이 있다는 알림
- 영업 부서
	- 영업 프로세스의 전체 수명주기, 단순한 이벤트가 아닌 장기적인 과정

### 충돌 상황
- 리드를 영업 부서의 정의대로 유비쿼터스 언어를 공표한다면 Over-Engineering이 반대의 경우 Under-Engineering이 발생함

### 전통적인 해결사항
1. 모든 종류에 대응 가능한 단일 모델 설게
   - 방대한 ERD 설계 > 데이터 일관성 유지에 복잡성 과다
2. 접두사를 통한 분류(마케팅 리드, 영업리드)
	a. 인지 부화를 일으킴
		 - 특정상황때 마다 분류를 해야되는 문제상황 직면
	b. 모델의 구현이 유비쿼터스 언어와 일치하지 않음
		- 아무도 대화에 접두사를 사용하지 않음

이를 해결하기 위한 도메인 주도 설계 패턴 **바운디드 컨텍스트(bounded context)**
>유비쿼터스 언어를 여러 개의 작은 언어로 나눔
	- 마케팅 컨텍스트
		- 리드 = 이벤트
	- 영업 컨텍스트
		- 리드 = 복잡한 엔티티

# 1. 바운디드 컨텍스트
- 모델은 경계 없이 존재할 수 없다.
	- 하나의 언어는 하나의 (명시적인)컨텍스트 안에 속한다.
- 물리적 경계와 소유권 경계를 규정하기 위한 도메인 주도 설계 도구
## 1.1. 바운디드 컨텍스트의 범위
- 전략적인 설계 의사결정으로 크기에 정답은 없음
	- 크기가 클수록
		- 유비쿼터스 언어의 일관성을 유지하기 어려움
	- 크기가 작을수록
		- 설계를 통합하는 오버헤드가 커짐
		- **해당 컨텍스트가 독립적으로 발전하는 능력을 저해**

# 2. 바운디드 컨텍스트 vs 하위 도메인
- 비즈니스 도메인을 분해하는 두 방법이 중복처럼 보이지만 그렇지 않다.
## 2.1. 하위 도메인을 통한 분해
- 하위 도메인은 비즈니스에 의해서 정의됨
- 하지만 소프트웨어 엔지니어는 하위 도메인을 식별하기 위해 비즈니스 도메인을 분석함

## 2.2. 바운디드 컨텍스트을 통한 분해해
- 바운디드 컨텍스트는 소프트웨어 엔지니어에 의해 설계됨

## 2.3. 하위 도메인과 바운디드 컨텍스트 사이의 상호작용
- 컨텍스트와 하위 도메인의 관계는 전략적인 선택임
- 그럼에도 중요한 점은 **하위 도메인 발견 후 바운디드 컨텍스트를 설계함**

# 3. 경계
## 3.1. 물리적 경계
- 바운디드 컨텍스트는 모델 경계 뿐만, 아니라 구현하는 시스템의 물리적 경계 역할
	- 서비스/프로젝트의 구현, 진화, 버전관리가 독립적으로 시행됨

## 3.2. 논리적 경계
- 바운디드 컨텍스트가 여러 하위 도메인을 포함할 때
	- 바운디드 컨텍스트 = 물리적 경계
	- 하위 도메인 = 논리적 경계

## 3.3. 소유권 경계
- 바운디드 컨텍스트는 한 팀만 소유해야 한다.
