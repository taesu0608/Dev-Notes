**애그리게이트 설계원칙**
>한 트랜잭션에서는 오직 하나의 애그리게이트 인스턴스만 변경한다.

# 1. 도메인 모델 패턴
복잡한 비즈니스 로직을 다루기 위함
## 1.1. 도메인 모델 구현
**도메인 모델**: 행동(behavior) + 데이터(data)를 포함하는 도메인의 객체 모델
**DDD 전술 패턴 종류**
- Aggregate
- Value Object
- Domain Event
- Domain Service
**DDD 전술 패턴들의 공통점**
- 비즈니스 로직을 최우선으로 둔다.
	- 설계 관심사에 따라 달라짐

## 1.2. 복잡성
- 비즈니스 로직은 본질적으로 복잡하므로 모델링되어지는 객체에 우발적 복잡성이 더해지면 안됨
- 우발적 복잡성
	- 데이터 베이스
	- 외부 시스템 구성요소
	- 인프라
- **[[POJO]]** 지향

## 1.3. 유비쿼터스 언어
- 도메인 모델 패턴은 유비쿼터스 사용으로 연결됨

# 2. 구성요소

## 2.1. 밸류 오브젝트 (Value Object)
- 복합적인(composition) 값에 의해 식별되는 객체
- 값이 식별자의 역할을 함
- Ex) 색 - (255,255,0)
### 2.1.1. 원시타입으로 구성된 객체체
- **원시 집착 코드 징후(primitive obsession code smell)**: 문자열(String), 정수(integer), 딕셔너리(dictionary)과 같은 원시 데이터 타입에 의존한 비즈니스 도메인
- **문제점**
	1. 유효성 검사 로직이 중복됨
		- 원시타입의 입력은 유효성 검사가 강제됨
	2. 값이 사용되기 전 유효성 검사 로직 호출이 어려워짐

#### 원시타입으로 구성된 Person
```java
class Person
{
	private int _id;
	private string _firstName;
	private string _lastName;
	private string _landlinePhone;
	private string _mobilePhone;
	private string _email;
	private int _heightMetric;
	private string _countryCode;
	
	public Person(...) {...}
}

static void Main(string[] args)
{
	var dave = new Person(
		id: 30217,
		firstName: "Dave",
		lastName: "Ancelovici",
		landlinePhone: "023745001",
		mobilePhone: "0873712503",
		email: "dave@learning-ddd.com",
		heightMetric: 180,
		countryCode: "BG");
	)
}
```

### 2.1.2. Value Object로 구성된 객체
- **장점**
	1. 명료성 향상
		- Ex) 변수명 변경 `CountryCode` > `country`
	2. 유효성 검사 로직
		- Value Object 자체에 유효성 검사 존재
		- Value Object가 유비쿼터스 언어를 사용함
#### Value Object Person
``` java
class Person
{
	private PersonId _id;
	private Name _name;
	private PhoneNumber _landline;
	private PhoneNumber _mobile;
	private EmailAddress _email;
	private Height _height;
	private CountryCode _country;
	
	public Person(...) {....}
}

static void Main(String[] args)
{
	var dave = new Person(
	id: new PersonId(30217),
	name: new Name("Dave", "Ancelovici"),
	landline: PhoneNumber.Parse("023745001"),
	mobile: PhoneNumber.Parse("0873712503"),
	email: Email.Parse("dave@learning-ddd.com"),
	height: Height.FromMetric(180),
	country: CountryCode.Parse("BG"));
	)
}
```
- Value Object
	- PersonId, Name, PhoneNumber, ... etc

### 2.1.3. Value Object = 불변의 객체

- 밸류 오브젝트는 불변의 객체로 구현된다.
    - 필드 값이 바뀌면 새로운 객체를 생성 (즉, 다른 객체로 취급)
    - Ex) Java의 `String`

**특징**
- 모든 연산자는 항상 새로운 객체를 반환
- 동일성(identity) 개념은 없고, 동등성(equality) 비교로만 구분
- `equals`와 `hashCode`는 값 기반으로 구현해야 함
- 구현 시 `final` 필드, setter 제거 → 진정한 불변성 보장
- 불변성 덕분에 참조 안전성, 스레드 안정성을 확보

## 2.2. 엔티티 (Entity)

### 2.2.1. Difference between Value Object and Entity
1. 식별자 필요
2. 식별자는 Entity의 생애주기 내내 불변
> 도메인 모델 패턴에서 Entity는 필수적 요소가 아니다.
> Aggregate 패턴에서만 Entity가 구현하기 때문

### 2.2.2. Aggregate
- Aggregate(총합합) = entity + @
**목적**
- 데이터의 일관성 보호
**특징**
- 명확한 경계 > 일관성 강화
	- 애그리게이트 = 일관성을 강화하는 경계
- 애그리게이트 외부의 모든 프로세스, 객체는 Read 만 가능
- 애그리게이트의 `public interface`의 메서드를 통해 상태 변경
- 커맨드 = 애그리게이트의 `public interface method`

### 2.2.3. 커맨드 구현 방법
1. 애그리게이트 객체에 퍼블릭 메서드 구현
```java
public class Ticket
{
	public void AddMessage(UserId from, String body)
	{
		var message = new Message(from, body);
		messages.Append(message);
	}
}
```
2. 모든 입력값을 포함하는 파라미터 객체로 표현
```java
public class Ticket
{
	public void Execute(AddMessage cmd)
	{
		var message = new Message(cmd.from, cmd.body);
		messages.Append(message);
	}
}
```
- 필자는 커맨드 구조를 통하여 다형적 메서드 전달 선호

### 2.2.4. 애그리게이트의 동시성 관리
```java
public ExecutionResult Escalate(TicketId id, EscalationReason reason) {
	try
	{
		var ticket = _ticketRepository.Load(id);
		var cmd = new Escalate(reason);
		ticket.Execute(cmd);
		_ticketRepository.Save(ticket);
		return ExecutionResult.Successs();
	}
	catch (ConcurrencyException ex)
	{
		return ExecutionResult.Error(ex);
	}
}
```
- 동시성 상황에서 발생할 문제를 발생하기 위해, 보통 나중의 프로세스는 의사결정에 사용된 상태가 만료되었다는 것은 통지받고 오퍼레이션을 재시도 한다.
1. 버전 필드를 애그리게이트에서 관리
- 가장 간단한 형태
```java
class Ticket
{
	TicketId _id;
	int _version;
}
```

```sql
UPDATE tickets
// 현재 ticket 상태와 파라미터 입력된 ticket 상태 확인 이후 설정

agg_version = agg_version + 1
```

### 2.2.5. 트랜잭션 경계
- 애그리게이트의 상태는 자신의 비즈니스 로직에 의해서만 수행
- 따라서 보통 애그리게이트 = 트랜잭션의 경계
- 모든 애그리게이트 상태 변경은 원자적 단일 오퍼레이션으로 트랜잭션 처리 되야함
	- 애그리게이트 상태 수정시, 모든 변경이 커밋되거나 롤백되어야 함
- 다중 애그리게이트 트랜잭션을 지원하는 시스템 오퍼레이션은 없다고 가정


### 2.2.6. Different between Entity and Aggregate
- aggregate = Entity + Value Object
#### Ex) 애그리게이트의 일관성 보장

```java
		if (this.IsEscalated && this.RemainingTimePrecentage < 0.5 && GetUnreadMessageCount(for: AssignedAgent) > 0)
		{
			... agent = AssignNetAgent();
```

### 2.2.7. 내부 애그리게이트 다른 객체 조작
1.  애그리게이트 루트를 통해 내부 Entity 수정
- 애그리게이트 루트 (Ticket)을 통해 내부 Entity (Message) 수정
```java
public class Ticket
{
	List<Message> _messages;
	
	public void Execute(AcknowledgeMessage cmd)
	{
		var message = _messages.Where( x => x.Id = cmd.id).First();
		message.WasRead = true;
	}
}
```

2. 도메인 이벤트
- **도메인 이벤트**: 비즈니스 도메인에서 일어나는 중요한 이벤트를 설명하는 메시지
- **특징**
	- 애그리게이트의 퍼블릭 인터페이스의 일부
```java
public class Ticket
{

	private List<DomainEvent> _domainEvents;
	...
	
	public void Excute(RequestEscalation cmd)
	{
		// 상부에 보고되지 않았고 잔여시간이 만료되었다면

		{
```

## 2.3. 도메인 서비스
- **도메인 서비스**: 비즈니스 로직을 구현한 상태가 없는 객체(stateless object)
### Ex) 상태가 없는 객체(stateless object)
```java
public class ResponseTimeFrameCalculationService
{
	...
	public ResponseTimeframe CalculateAgentResponseDeadline(UserUd agentId, Priority priority, bool escalated, DateTime startTime)
	{
		var policy = _departmentRepository.GetDepartmentPolicy(agentId);
		var maxProcTime = policy.GetMaxResponseTimeFor(priority);
		
		if (escalated) {
			maxProcTime = maxProcTime * policy.EscalationFactor;
		}
		
		var shifts = _departmentRepository.GetUpcomingShifts(agentId, startTime, startTime.Add(policy.MaxAgentResponseTime));
		
		return CalculateTargetTime(maxProcTime, shifts);
	}
}
```
- **한 개의 트랜잭션이 한 개의 인스턴스(어그리게이트)를 갖는 규칙 따름**
- 여러 애그리게이트의 데이터를 **READ**함으로써 부분적 한계를 해소

### 2.3.1. 복잡성
- 시스템의 복잡성의 인과요소
	- 제어의 어려움
	- 동작 예측의 어려움
- 시스템의 복잡성 = 시스템의 자유도
- 시스템의 자유도 = 데이터 요소의 개수
#### Ex) 데이터 요소수에 따른 시스템의 자유도
```c#
public class ClassA
{
	public int A { get; set; }
	public int B { get; set; }
	public int C { get; set; }
	public int D { get; set; }
	public int E { get; set; }
}

public class ClassB
{
	private int _a, _d;
	
	public int A
	{
		get => _a;
		set{
			_a = value;
			B = value / 2;
			C = value / 3;
		}
	}
	
	public int B {get; private set;}
	public int C {get; private set;}
	public int D
	{
		get => _d;
		set {
			_d = value;
			E = value * 2;
		}
	}
	
	public int E {get; private set;}
}
```
- ClassA의 자유도 (필요한 데이터 요소): 5
	- 복잡도 5
- ClassB의 자유도 (필요한 데이터 요소): 2
	- 복잡도 2
