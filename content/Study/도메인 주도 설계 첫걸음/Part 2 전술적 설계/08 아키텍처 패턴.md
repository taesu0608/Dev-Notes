# 1. 비즈니스 로직과 아키텍처 패턴
-  코드베이스의 설계의 어려운점
	- 기능이 중복되고, 분할될 수 있음
	- 영향력이 잠재적이다.
- 아키텍처 패턴의 적용은 비즈니스 로직 구현 지원 + 유지 보수 를 도움
- **주요 아키텍처**
	1. 계층형 아키텍처
	2. 포트와 어댑터
	3. CQRS

## 1.1. 계층형 아키텍처 (layered architecture)
- **구조**
	- 프레젠테이션 계층(PL: presentation layer)
	- 비즈니스 로직(BLL: business logic layer)
	- 데이터 접근 계층(DAL: data access layer)

### 1.1.1. 프레젠테이션 계층
- **목적**: 사용자와 상호작용을 위한 프로그램의 사용자 인터페이스 구현
- Ex) 웹 인터페이스, 데스크톱 인터페이스

현대에서 광역적으로 의미가 넓어짐
- **광역적 현대의 목적**: 프로그램의 **동작을 촉발**하는 모든 동기식 or 비동기식 수단
- Ex) 현대 PL
	- 그래픽 사용자 인터페이스(GUI)
	- 커맨드 라인 인터페이스(CLI)
	- 다른 시스템과 연동하는 프로그래밍 API
	- 메시지 브로커에서 이벤트에 대한 구독
	- 나가는 이벤트를 발행하는 메시지 토픽

### 1.1.2. 비즈니스 로직 계층
- **목적**: 프로그램의 비즈니스 로직을 구현함
- Ex) 엑티브 레코드, 도메인 모델

### 1.1.3. 데이터 접근 계층
- **목적**: 영속성 메커니즘(Ex) Database)에 접근을 위함
- **광역적 현대의 목적**
	1. NoSQL 출현이후 여러 목적의 DB를 사용함
		- 실시간 데이터 처리 - 도큐먼트 저장소
		- 동적 질의 - 검색 인덱스
		- 최적화된 성능 - 인메모리 데이터베이스
	2. 정보 저장용 또한 여러 목적의 매체 사용
		- 클라우드 기반 오브젝트 저장소
		- 메시지 버스
	3. 외부 API 접근
		- 주식 데이터, 오디오 녹음
		- 클라우드 벤더의 관리형 서비스

### 1.1.4. 계층 간 커뮤니케이션
- **탑다운(top-down)** 커뮤니케이션 모델
	- 각 계층은 아래 계층에만 의존

### 1.1.5 변종(variation)
- **서비스 계층**
```C#
namespace MvcApplication.Controllers
{
	public class UserController: Controller
	{
		...
		[AcceptVerbs(HttpVerbs.Post)]
		public ActionResult Create (ContactDetails contactDetails)
		{
			OperationResult result = null;
			
			try
			{
				..db.StartTransaction();
				
				// Business layer
				var user = new User();
				user.SetContactDetails(contactDetails)
				user.Saver();
				
				// Service layer
				..db.Commit();
				result = OperationResult.Success;
			} catch (Exception ex){
				..db.Rollback();
				result = OperationResult.Exception(ex);
			}
			
			return View(result)
		}
	}
}
```
- 프레젠테이션 계층과 비즈니스 로직의 결합을 제거하기 위해 서비스 로직 사용
- 프레젠테이션 > 서비스 > 비즈니스 로직 > 데이터 접근

**서비스 계층은 논리적 경계이다.**

```C#
interface CampaignManagementService
{
	OperationResult CreateCampaign(CampaignDetails details);
	OperationResult Publish(Campaign id, PublishingSchedule schedule);
	OperationResult Deactivate(CampaignId id);
	OperationResult AddDisplayLocation(CampaignId id, DisplayLocation newLocation);
}
```

```C#
namespace ServiceLayer
{
	public class UserSerivce
	{
		public OperationResult Create(ContactDetails contactDetails)
		{
			OperationResult result = null;
			
			try
			{
				db.StartTransaction():
				
				var user = new User();
				user.SetContactDetails(contactDetails);
				user.Save();
				
				db.Commit();
				result = OperationResult.Success;
			} catch (Exception ex){
				db.Rollback();
				result = OperationResult.Exception(ex);
			}
			
			return result;
		}
	}
}

namespace MvcApplication.Controllers
{
	public class UserController:Controller
	{
		[AcceptVerbs(HttpVerbs.Post)]
		public ActionResult Create(ContactDetails contactDetails)
		{
			var result = _userService.Create(contactDetails);
			return View(result);
		}
	}
}
```

**서비스 계층의 장점**
- 동일한 서비스 계층 재사용
- 모듈화: 관련 메서드들끼리 밀집도가 올라감
- 프레젠테이션 계층과 비즈니스 로직 계층의 결합도를 낮춤
- 비즈니스 기능 테스트에 용이함

트랜잭션 스크립트와 같은 경우 이미 메서드 노출을 통해 비즈니스 로직이 진행됨
- 서비스 계층, 비즈니스 로직 계층 둘 중 하나만 구성
액티브 레코드 패턴에서 레코드가 외부에서 조율이 필요한 경우 서비스 계층이 필요함
- 서비스 계층으로 트랜잭션 스크립트 패턴 구현
- 비즈니스 로직계층으로 액티브 레코드 구현

### Cf) 용어
- 프레젠테이션 계층 = 사용자 인터페이스 계층
- 서비스 계층 = 애플리케이션 계층
- 비즈니스 로직 계층 = 도메인 계층 = 모델 계층
- 데이터 접근 계층 = 인프라스트럭처 계층

##### 도메인 모델 패턴과 계층형 아키텍처는 충돌점이 분명하다
> 도메인 모델 패턴은 도메인이 계층으로부터 비종속적이길 바란다.

### Cf) 계층과 티어
> 계층형 아키텍처와 N-티어(N-Tier) 아키텍처는 혼동될 때가 많다.

계층
- 논리적 경계
- 모든 계층은 동일한 수명주기에 속함
티어
- 물리적 경계
- 독립적으로 배포될 수 있는 서비스,서버,시스템

## 1.2. 포트와 어댑터(port & adapter)
- **특징**
	- 포트: 비즈니스 로직 계층은 인프라스트럭처 계층의 구현체의 규칙(**포트**)을 정의한다.
	- 어댑터: 포트의 인터페이스의 실질적 구현체
### 1.2.1. 용어
- 인프라스트럭처 계층
	- 프레젠테이션 계층 + 데이터 접근 계층
	- 데이터 베이스 + UI 프레임워크 + 외부 제공자 + 메시지 버스

## 1.3. CQRS(command-query responsibility segregation) 패턴
- **목적**
	- CQRS 패턴은 이벤트 소싱의 질의 한계를 극복하기 위함
	- 이벤트 소싱 패턴 구현에 적합
	- 다양한 영속 모델 사용에 적합
### 1.3.1. 폴리글랏 모델링
- 모든 데이터베이스는 결점이 존재 이를 해결하기 위한 영속성 모델
	- OLTP(online transaction processing)
		- **목적**: 운영 트랜잭션 처리
	- OLAP(online analytical processing)
		- **목적**: 데이터 분석/ 의사 결정

- 영속성 모델(polyglot persistence model)
	- 여러 데이터베이스를 사용하는 것

### 1.3.2. 구현
- 시스템 모델의 책임 분리를 위한 구성요소
	1. 커맨드 실행 모델
		- 커멘드
		- 질의(수정 O)
	2. 읽기 모델
		- 질의(수정 X)

- 커맨드 실행 모델(command execution model)
	- CQRS에는 시스템의 상태를 수정하는 오퍼레이션(시스템 커맨드)을 전담으로 수행하는 단일 모델
	- 비즈니스 로직 구현, 규칙 검사, 불변성 강화
	- 비즈니스 엔티티의 일관적 상태 유지 + 갱신할 때 낙관적 동시성

- 읽기 모델(projection)
	- 캐시에서 언제든 다시 추출할 수 있는 프로젝션
	- 관계형 데이터베이스의 머터리얼라이즈 뷰(materialized view)의 개념과 유사

****
1. 동기식 프로젝션(synchronous projection)
	- ##### 세이브포인트 방식
	- 격차 해소 구독 모델(catch-up subscription model)로 OLTP 데이터의 변경사항을 가져옴
	- **격차 해소 구독 모델 과정**
		1. 프로젝션 엔진이 OLTP 데이터베이스로부터 체크포인트 이후 추가/갱신 된 레코드 조회
		2. 프로젝션 엔진이 조회된 데이터를 이용해 시스템의 읽기 모델 재생성/갱신
		3. 프로젝션 엔진은 마지막으로 처리 레코드의 체크포인트를 저장. 이 값은 다음 처리 때 추가되거나 갱신된 레코드를 조회하는데 사용
	- 프로젝션: 이벤트 소싱(Event Sourcing)이나 기타 영속 저장소에 저장된 데이터를, 시스템에서의 읽기/조회, 리포트, UI 처리 등에 적합한 모델(읽기 모델, 뷰 모델 등)로 변환하는 것
	- 프로젝션 엔진: 프로젝션을 시행하는 소프트웨어 모듈
	- 체크포인트: 순차적으로 값이 증가하는 checkpoint 컬럼 설정

2. 비동기 프로젝션
	- 모든 커밋된 변경사항을 메시지 버스(Me)에 발행

- **문제점**
	- 비동기 프로젝션 방식
		- 확장성, 성능의 장점 but 분산 컴퓨팅에서 문제발생
			- 메시지 순서, 중복처리
	- CQRS의 궁극적 한계
		- 궁극적 일관성은 즉각적인 갱신이 불가하다.
		> Command execution model과 projection의 궁극적 일관성은
		> Command execution model을 통한 수정 요청이 projection에 반영되기 까지의 시간이 필요하다.
		> 따라서 현대의 일관성은 효율화된 응답을 위해 Command execution model은 수정된 값을 반환되게 설정한다. 이 방식은 높은 일관성을 유지하긴 하지만 완벽한 일관성은 포기한 방법이다.
