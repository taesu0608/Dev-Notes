## 2.1. 이벤트 소싱 도메인 모델
- **장점**
	- 과거 상태 재구성
		- 비즈니스 로직 타당성(동작 분석, 의사결정 검사)을 목적
		- 소급 디버깅(retroactive debugging)
			- 버그 관찰 이전 상태로 되돌림
	- 핵심 하위 도메인 최적화
		- 기존 이벤트의 데이터를 활용하여 최적화된 비즈니스 로직 제공
			- 이벤트 유형에 따른 이벤트 로직 오버로딩
	- 감사 로그(audit log)
		- 자동화된 로그
	- 고급 낙관적 동시성 제어
		- 고급 낙관적 동시성 모델은 덮어 쓰기시 예외를 발생
		- 예외 발생시, 어떠한 상황 발생인지 케이스 분류 가능
			- 케이스에 따른 이벤트 설계를 통하여 도메인 주도 의사결정 가능
- **단점**
	- 학습 곡선
		- 이벤트 소싱 시스템을 구현한 경험이 있어야함
	- 모델의 진화
		- 이벤트 소싱 모델의 발전은 어려움
		- 이벤트 소싱에서 이벤트는 변경되어선 안됨
			- 스키마 조정시, 어려움이 있음
			- Cf) Versioning in an Event Sourced System 서적 참고
	- 아키텍처 복잡성
		- 이벤트 소싱 구현시 유동적인 부분이 도입됨
- **성능**
	- 애그리게이트 상태 재구성, 이벤트 추가시 성능이 저하됨
		- Ex) 애그리게이트당 10,000개 이상의 이벤트 존재시 성능저하
		  평균적으로 100개 이벤트를 초과하지 않음
		- 다른 패턴 적용 고려 필요(스냅숏 패턴)
### 2.1.1.이벤트 소싱 애그리게이트 단계
1. **도메인 이벤트 로드**
    - 기존 이벤트가 있다면 불러옴.
    - 최초 생성 시에는 **빈 스트림**.
2. **상태 재구성(리하이드레이션)**
    - 불러온 이벤트가 있으면 apply해서 상태 복원.
    - 없으면 그냥 “init 상태” (예: `new OrderAggregate()` → 아직 어떤 불변식도 충족 안 된 상태).
3. **명령 실행 → 이벤트 생성**
    - `CreateOrder` 명령 같은 걸 실행하면서 **최초 이벤트**(`OrderCreated`) 발생.
4. **스토어에 커밋**
    - expectedVersion = 0 으로 append → 이벤트 스토어에 최초 이벤트 저장.

```C#
public class TickerAPI
{
	private ITicketsRepository ..ticketsRepository;
	
	public void RequestEscalcation(TicketId id, ExcalationReason reason)
	{
		// 로드
		var events = _ticketsRepository.LoadEvents(id);
		// 리하이드레이션
		var ticket = new Ticket(events);
		var originalVersion = ticket.Version;
		// 실행
		var cmd = new RequestEscalation(reason);
		ticket.Execute(cmd);
		// 커밋
		..ticketsRepository.CommitChanges(ticket, originalVersion);
	}
}
```

### Cf) 왜 `이벤트 소싱 도메인 모델`일까?
> 이벤트 소싱은 도메인 없이도 가능하다. 하지만 도메인 모델 애그리게이트의 수명주기 변경을 나타내기 위해 이벤트 소싱을 사용하고 있음을 명시적으로 표현하기 위해 작위적으로 명칭을 사용했다.

### Cf) 단일 애그리게이트 컨텍스트는 왜 ID 사용을 가능케 할까?
>단일 애그리게이트 컨텍스트에서는 한 트랜잭션이 오직 하나의 애그리게이트만 수정한다는 규칙이 보장되므로, 이벤트 스토어는 각 애그리게이트를 ID 단위의 독립적인 스트림으로 다룰 수 있다. 따라서 동시성 제어도 객체 전체를 잠그거나 상태를 직접 비교할 필요 없이, 단순히 해당 애그리게이트의 **ID와 버전(expectedVersion)** 만 확인하면 충분하다. 이 원칙 덕분에 시스템은 복잡한 분산 락이나 트랜잭션 관리 없이도 가볍게 낙관적 동시성 제어를 구현할 수 있다.
- 하지만 애그리게이트의 인스턴스에 속하는 모든 이벤트는 단일 (shard)에 있어야 한다.

### 2.1.3. 페이로드 패턴(forgettable payload pattern)
>페이로드 패턴(payload pattern)은 이벤트 소싱 환경에서 **GDPR 같은 규제 때문에 특정 개인 데이터를 실제로 삭제할 수 없는 문제**를 우회하기 위한 전략이다. 이벤트 스토어 자체는 불변성을 전제로 하기 때문에 데이터를 지우거나 수정할 수 없지만, 이벤트의 **payload(실제 데이터 영역)** 안에는 민감한 정보를 직접 담는 대신 **외부 식별자나 토큰**을 넣어두고, 해당 토큰이 가리키는 별도의 저장소에서만 민감 데이터를 관리한다. 이렇게 하면 이벤트 스토어에는 개인정보가 남지 않고, 외부 저장소에서 토큰과 매핑된 데이터를 삭제하거나 익명화함으로써 GDPR의 "잊힐 권리" 요구를 충족시킬 수 있다.

### Cf) 데이터베이스와 로그파일 동시 관리가 어려운 이유
- 데이터베이스와 로그파일 모두 관리하는 것은 한 작업에 대해 두 저장장치를 사용하는 트랜잭션이다.
  데이터 페이스의 트랜잭션이 실패하면 로그파일의 메시지도 삭제되어야한다. 이는 구성이 어렵다.

### Cf) 상태 기반 모델 사용이 아닌 동일한 데이터베이스 트랜잭션에서 로그 테이블 운용
- 로그 레코드와 인스턴스 상태의 일관된 동기화를 목적으로한다. 하지만 추후 미래의 작업에서 적절한 코드 레코드를 추가 하지 않는다면 어떻게 대처해야 할까?

### Cf) 상태 기반 모델 사용이 아닌 레코드의 스냅숏을 통해 전용 '이력' 테이블에 복사하는 데이터베이스 트리거를 사용할 수 없는 이유
- 로그 테이블에 레코드를 추가하는 방식을 `Trigger`를 통해 자동 호출을 목적으로 하는 아이디어
- 변경 내용은 저장하지만 변경 목적(비즈니스 컨텍스트)를 잃게 됨
#### Ex) 비즈니스 컨텍스트를 읽는 경우
- **DB 트리거는 데이터 변경만 감지**
    - 트리거는 `INSERT/UPDATE/DELETE` 같은 상태 변화만 포착함
    - “왜 이 변경이 발생했는가?”라는 도메인 의도는 코드 레벨에서 알 수 없음
    - 로그 테이블에 `reason`, `context` 같은 칼럼 추가해도 결국 애플리케이션 로직에서 주입해야 함 → 트리거만으로는 불가능함
        
- **도메인 이벤트 ≠ 데이터 변경**
    - 이벤트 소싱의 이벤트는 “주문이 생성됨(OrderPlaced)”처럼 도메인 언어로 표현됨
    - 트리거는 “orders 테이블에 row 하나 insert 됨” 같은 저수준 데이터 조작만 알 수 있음
    - 즉, 이벤트 소싱은 **업무 의도 → 상태 반영** 순서, 트리거는 **상태 반영 → 로그 기록** 순서임
