# 1. 서비스란 무엇인가
## 1.1. 서비스란 In OASIS(Organization for the Advancement of Structured Information Standards)
- **미리 정의된 인터페이스**를 사용해 하나 이상의 역량에 접근하기 위한 메커니즘
	- 미리 정의된 인터페이스: 서비스로부터 데이터를 넣고 빼는 모든 메커니즘
		- 미리 정의된 인터페이스 2가지
			- 동기식: 요청/응답 모델 사용
			- 비동기식: 이벤트를 사용


## 1.2. 마이크로서비스란
- 서비스가 자신의 퍼블릭 인터페이스에 의해 정의됨
	- i.e.) 마이크로 퍼블릭 인터페이스(micro-front door)에 의해 정의되는 서비스
	-  퍼블릭 인터페이스: 외부 사용자가 서비스를 올바르게 사용하기 위해 알아야하는 모든 규칙과 계약을 명시적으로 표현한 것
### 1.2.1. 마이크로서비스 특징
1. 단일 서비스의 기능과 그 서비스가 연동하는 다른 시스템 구성요소 모두를 쉽게 이해 가능함
	- 내부 구현을 알지 못해도 되기 때문
2. 데이터베이스를 노출 시키지 않음
	- 관계형 데이터베이스의 노출은 과도한 `front-door`의 확장을 요구하는 것과 같음

### 1.2.2. 서비스형 메서드가 완벽한 마이크로 서비스일까?
- 서비스형 메서드: 각 서비스가 단일 메서드 만을 갖는 것
	-  서비스형 메서드의 단점
		1. 협력을 위한 퍼블릭 인터페이스의 필요성 증가
		2. 전체 시스템의 비효율성 증가
			- 각 서비스의 단일 메서드 관리는 용이
			- 전체 서비스의 복잡도 증가
		- Thus) 시스템의 목적과 양립불가능함

> 시스템의 목적
> 1. 함께 작동하는 연동된 것 또는 디바이스
> 2. 특정 목적을 위해 함께 사용되는 컴퓨터 장비 및 프로그램

### 1.2.3. 시스템의 복잡성
- **로컬 복잡성**: 각각의 개별 마이크로서비스의 복잡성
- **글로벌 복잡성**: 전체의 시스템의 복잡성
#### 시스템의 복잡성
- 로컬 복잡성과 글로벌 복잡성의 균형을 잡는 것이 중요함

## 1.3. 깊은 모듈로서의 마이크로 서비스

### 1.3.1. 깊은 모듈과 얕은 모듈
- 깊은 모듈: 서비스 내 로직 복잡성이 높은 모듈
- 얕은 모듈: 서비스 내 로직 복잡성이 낮은 모듈
	- ex) 메서드의 시그니처와 로직이 동일한 함수

> 모듈이 로직 복잡성을 내포하지 않으면 전체 시스템에 우발적 복잡성을 증가시킴
### 1.3.2. 모놀리식 서비스와 마이크로 서비스간의 변환 시 특징
- 극단적인 모놀리식 서비스의 경우
	- 모듈 간 결합도가 높아져 변경 영향 범위 예측이 어려움
	- 작은 수정에도 전체 애플리케이션을 함께 빌드 배포해야 함
	- 점진적 기술 전환이 어려움
- 극단적인 마이크로 서비스의 경우
	- 서비스 간 통신이 과도하게 분산됨
	- 트랜잭션이 여러 서비스로 나뉘어 일관성 보장이 복잡해짐
	
## 1.4. 도메인 주도 설계와 마이크로서비스의 경계

### 1.4.1. 바운디드 컨텍스트와 마이크로서비스
- 마이크로 서비스와 바운디드 컨텍스트 모두 물리적 경계를 표시함
- 모든 마이크로 서비스는 바운디드 컨텍스트로 볼 수 있음
	- 모든 바운디드 컨텍스트가 마이크로 서비스는 아니다.

- 바운디드 컨텍트스와 마이크로 서비스 사이의 서비스를 추가해야함
### 1.4.2. 애그리게이트와 마이크로서비스
**애그리게이트**: 내부 비즈니스  규칙과 불변성, 로직의 복잡성을 감싸는 개별적인 비즈니스 기능 단위
- 애그리게이트는 마이크로서비스의 최소 단위로 취급되어지기도 함

### 1.4.3. 하위도메인과 마이크로서비스
- 마이크로서비스를 설계하는 데 있어 하위 도메인은 중요한 비즈니스 설계 기준이 됨
- 일반적으로 하위 도메인의 경계와 마이크로서비스의 경계를 일치시키는 방식이 권장
- 하위 도메인은 ‘어떻게 구현할 것인가’보다 ‘무엇을 책임지는가’에 초점을 둔 개념
- 모든 하위 도메인이 반드시 마이크로서비스로 구현될 필요 없음
- Thus) 하위 도메인은 비즈니스가 다루는 문제 영역을 의미적으로 구분한 개념이며, 마이크로서비스를 설계할 때 매우 유용한 기준이 된다. 특히 하위 도메인은 구현 방식보다는 책임과 역할에 초점을 두기 때문에, 자연스럽게 높은 응집도를 가지는 구조로 설계된다. 이러한 특성으로 인해 하위 도메인의 경계를 마이크로서비스의 경계와 일치시키는 방식은 직관적이며 설계 측면에서도 많은 이점을 가진다. 
  이러한 접근 방식에서는 하나의 하위 도메인이 하나의 마이크로서비스로 대응되며, 해당 서비스는 비교적 적은 수의 퍼블릭 인터페이스를 노출하고 내부적으로는 높은 구현 복잡도를 가질 수 있다. 이는 서비스 외부에서 바라볼 때 단순한 사용성을 제공하면서도, 내부적으로는 도메인 로직을 충분히 캡슐화할 수 있다는 장점을 가진다. 
  반면, 하나의 하위 도메인을 지나치게 세분화하여 여러 개의 퍼블릭 인터페이스와 서비스로 나누게 되면, 각 구성 요소의 구현 난이도는 낮아질 수 있으나 시스템 전체의 복잡도는 오히려 증가하게 된다. 서비스 간 호출이 늘어나고, 의존성이 복잡해지며, 변경에 따른 영향 범위도 커지게 된다.
  또한 모든 하위 도메인을 반드시 마이크로서비스로 분리해야 하는 것은 아니다. 실제 시스템 설계에서는 비즈니스 도메인의 특성뿐만 아니라 조직 구조, 팀의 규모, 배포 및 운영 전략, 성능 요구사항과 같은 비기능적 요소들이 함께 고려되어야 한다. 이러한 이유로 어떤 하위 도메인은 마이크로서비스로 구현되기도 하고, 어떤 경우에는 하나의 애플리케이션 내부 모듈이나 애그리게이트 수준으로 구성되는 것이 더 적절할 수도 있다.

# 1.5. 마이크로서비스의 퍼블릭 인터페이스 압축하기
- 퍼블릭 인터페이스를 압축하는 방법
	- **오픈 호스트 서비스**
	- **충돌 방지 계층**

### 1.5.1. 오픈 호스트 서비스
#### 오픈 호스트 서비스 특징
1. 시스템의 글로벌 복잡성이 줄어든다.
	- 공표된 언어를 통한 개발은 새로운 모델 구현시 변환의 편리함을 가져다 준다.
2. 공표된 언어는 좀 더 제한된 모델을 노출한다.
	- 퍼블릭 인터페이스의 간소화는 깊은 모델 설계를 유도하고 이는 효과적인 마이크로서비스 설계를 기여한다.

### 1.5.2. 충돌 방지 계층 (ACL)
#### 충돌 방지 계층 특징
- 바운디드 컨텍스트와 연동할 때 복잡성을 줄여준다.
- 로컬 복잡성과 시스템 복잡성 모두를 줄여준다.
- 연동 복잡성을 별도로 담당하는 개별 서비스화 되기도 한다.
